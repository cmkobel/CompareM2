# Issue #156 — panaroo aborts on Bakta selenocysteine CDS, 2026-10-09

Patrick Biggs, ~140 genomes, CompareM2 3.4, WSL2. panaroo, snp-dists and
fasttree failed; mlst and mashtree (same `perl` environment) succeeded, so the
environment built and panaroo failed at runtime.

## Cause

His traceback ends in `panaroo/prokka.py` line 207 → `ValueError: Invalid gene
sequence!` → `RuntimeError: Error reading prokka input!`. Line 207 is the
*second* raise in `get_gene_sequences` in panaroo 1.6.1–1.8.0 (1.5.x–1.6.0 have
it at 204): a CDS whose length is not a multiple of 3, is under 34 nt, or
translates with an internal `*`. Without `--remove-invalid-genes` that is fatal
for the whole run. snp-dists and fasttree read panaroo's alignment, so they go
with it. Nothing to do with Python 3.14 or his own panaroo install attempt —
the traceback is from the CompareM2-built env (`python3.12`).

The panaroo env name in his traceback is `b1d4402d…`, under `~/.comparem2/envs`.
"0/35" in his progress bar is panaroo's chunking: ceil(140 / 4) = 35, so it ran
with 4 threads and died in the first chunk of 4 genomes.

**Bakta writes selenoproteins as one CDS read through the TGA**, with
`transl_except=(pos:…,aa:Sec)` (de novo since Bakta 1.4, commit `d159f3f9`,
2022-03-17). Panaroo reads that TGA as a premature stop.

## Reproduced on thylakoid — `/evo/postdoc/scratch/issue156/`

Bakta 1.12.1, db-light (the DB CompareM2 fetches), panaroo 1.8.0, CompareM2's
exact command line `panaroo --clean-mode strict -a core -t 4 -o … -i …`.

| input | Sec CDS | edge CDS | panaroo, no flag | with `--remove-invalid-genes` |
| --- | --- | --- | --- | --- |
| *E. coli* K-12 MG1655 + O157:H7 Sakai | 3 + 3 | 0 | **exit 1 in 1 s**, Patrick's traceback | exit 0 in 239 s, 6 genes dropped, `core_gene_alignment_filtered.aln` and `.Rtab` written |
| *C. jejuni* NCTC 11168 + a rotated copy | 0 + 0 | 0 | exit 0 in 74 s | exit 0 in 74 s |

The three in K-12 are fdnG (3,048 nt), fdoG (3,051 nt), fdhF (2,148 nt). The
`invalid gene! file - id: …` line that names the gene is **absent from the
failing log** — it is printed in a loky worker and lost when the worker raises —
which is why Patrick's log does not say which gene.

Panaroo issue gtonkinhill/panaroo#373 (open, 2026-04-04) reports the same thing
on 1.6.0 and claims the flag does *not* help. On 1.8.0 it does — row 1 above.

Not established: Patrick's species. *C. jejuni* NCTC 11168 gets no Sec CDS from
Bakta light, so if his set is *Campylobacter* the cause needs re-checking; the
discriminating check is `grep -l transl_except results_comparem2/samples/*/bakta/*.gff3`.

## Ruled out

- **Bakta pseudogenes** would also trip line 207, but Bakta skips pseudogene
  detection with the light DB (`main.py:341`), and CompareM2 fetches light.
- **Origin-spanning CDS** (`edge`, written with `stop > contig length`) cannot
  cause this crash. Bakta only merges an edge CDS when the two partials end
  exactly at 1 and at the contig length, and prodigal partials are
  codon-aligned, so the slice panaroo takes is always a multiple of 3 with no
  internal stop. It passes **silently as a truncated gene**: the demo's
  `ISMMS_VRE_1` contig_1 has `56152..57825` on a 57,543 nt contig, of which
  panaroo sees 1,392 of 1,674 nt. One gene per affected circular replicon;
  panaroo's fragment handling may absorb it. Not fixed by the flag. Recorded,
  not acted on.

## Second defect: `--set` is silently dropped for 7 of 14 tools

Probing every spec with an override `(("--PROBE", "x"),)` through
`snakefile._ctx`: the flag reaches the command for bakta, amrfinder, mashtree,
treecluster, skani, carveme, biosynthesis — and **not** for seqkit, checkm2,
gtdbtk, mlst, panaroo, snp-dists, fasttree, whose `command` lambdas never
splice `*c.args()`. `parse_overrides` accepts the setting without complaint.
`docs/06 cheat sheet.md` §5 and `docs/20 usage.md` present `--set` as working
for any tool. So Patrick has no CLI workaround in 3.4.

## Proposed fix — applied 2026-10-09 by the 3.5.0 release session

Applied as below, plus `*c.args()` spliced into the other six commands before
their positional inputs, and `test_every_command_carries_its_params`. Not yet
re-run on Patrick-like input after the change; the reproduction above is the
evidence for the flag.


```python
panaroo = Tool(
    ...
    command=lambda c: [
        "panaroo", "--clean-mode", "strict", "-a", "core", "-t", str(c.threads),
        "-o", str(c.out("panaroo")), *c.args(),
        "-i", *[str(c.sample_out(s, "bakta", f"{s}.gff3")) for s in c.samples],
    ],
    # Bakta writes a selenoprotein as one CDS read through its TGA
    # (`transl_except=Sec`); panaroo reads that as a premature stop and, without
    # this flag, aborts the whole run on the first one — every E. coli has three.
    params=(("--remove-invalid-genes", ""),),
    ...
)
```

Plus a test that every tool's command carries its params (the probe above),
which forces a decision on the other six: splice `*c.args()` into each, or have
`parse_overrides` refuse a tool that ignores them. The docs promise the former.
Doc sync: the panaroo default in `docs/` where command lines are listed,
`DECISIONS.md` (why the flag), `STATUS.md` (the reproduction above).
