## Two `optimal` answers from one build on one file — expected for this conditioning?

SCIP 10.0.3, SoPlex 8.0.3, PaPILO 3.0.1 — conda-forge `linux-64`,
`scip-10.0.3-h311443d_0`.

The attached `carveme_116_2.lp` is a genome-scale metabolic model
reconstruction generated by [CarveMe](https://github.com/cdanielmachado/carveme):
11811 variables of which 6279 binary, 14027 constraints, maximisation. Each
continuous flux is coupled to an indicator with big-M 1e3 against eps 1e-3.

All four runs with `set limits gap 0.001`:

```
scip -c "read carveme_116_2.lp set limits time 300 set limits gap 0.001 optimize quit"
    -> time limit, primal 913.500, dual 935.696

scip -c "read carveme_116_2.lp read carveme_947.sol set limits time 300 set limits gap 0.001 optimize quit"
    -> "1/1 feasible solution given by solution candidate storage"
       gap limit, primal 947.500, dual 947.796

scip -c "read carveme_116_2.lp read carveme_943.sol set limits time 300 set limits gap 0.001 optimize quit"
    -> optimal, 943.500, in 5.1 s

scip -c "read carveme_116_2.lp set presolving milp maxrounds 0 set limits time 300 set limits gap 0.001 optimize quit"
    -> optimal, 947.500, in 7.5 s
```

So run 3 proves 943.500 optimal while run 2 accepts 947.500 as feasible, and
run 1's dual bound sits 11.8 below a point the same build certifies. Everything
changes only with `presolving/milp/maxrounds`; `misc/usesymmetry=0` makes no
difference, and a SCIP 10.0.2 built without PaPILO (the PyPI `pyscipopt` wheel)
does not show run 1's behaviour.

I do not want to file this as a soundness bug, because I suspect the scaling is
the whole story. Both solutions are feasible only to tolerance: largest
constraint violation ~5e-11, but integrality violation exactly 1e-6 against the
default `feastol`, and fixing either one's binaries to exact integers makes the
remaining LP infeasible. (Violations computed from the constraint coefficients
directly, not from the solver's own checker.)

So, two questions:

1. Is a dual bound below a tolerance-feasible incumbent expected at this
   conditioning, and is the MILP presolver more sensitive to it than the rest of
   the pipeline?
2. Is there a recommended parameter set for models of this shape, short of
   disabling `presolving/milp` — tightening `numerics/feastol` or
   `numerics/epsilon`, or rescaling before solving?

The practical reason for asking: this LP shape is what CarveMe generates for
every bacterial genome it reconstructs, and every conda-installed copy of it
solves with a PaPILO-linked SCIP. The difference for a user is a metabolic model
with 1193 reactions instead of 1742, after ten minutes instead of one.
